## Grounded findings and decisions

- The supplied handoffs, lifecycle research and skill audit were consumed. Existing `linear-triage` is intake/investigation, not delivery. Rename/move it to `linear-intake` before using the freed `linear-triage` name for delivery. This is a clean cutover: migrate consumers and evals; no alias that ambiguously routes delivery into intake.
- `linear-refinement` already owns requirement quality/OpenSpec plan readiness; extend it for project-bounded Backlog and Todo sweeps without claiming readiness on labels alone.
- `linear-cleanup` owns evidence reconciliation. Rename/move it to `linear-sync` and extend it to inspect all prior stage outcomes and send/update user-facing progress when requested/authorized. Do not add an always-on polling service.
- Preserve `linear-management` as the normative governance dependency. Its canonical portability source must be located/recovered from the already approved worktree before authoring; do not recreate or overwrite its governance rules from memory. `triage-linear` is a legacy redirect, not a workflow owner; remove it under clean-cutover and remove/update its eval/consumers.
- `orchestrator-patterns` provides agent-neutral delegation; `jcode-orchestration` and prompt files are optional native adapters. `apply`/`apply-all`, `gates`, `review`, `close`, `recovery`, and `jcode-handoff` remain the semantic owners for implementation, independent acceptance, artifact closure, recovery, and durable handoffs. Delivery `linear-triage` coordinates/pulls a task and orchestrates these; it must not duplicate them.
- The named Ant fork is not evidence of delivery orchestration: it is inherited design/proposal work and contains no task-pull, worker, worktree, PR, CI, review-comment, or cleanup operation. Use `apps/with-orca/WORKFLOW.md` and lifecycle research as proposed sequence evidence, not as portable installed capabilities. Explicitly author delivery behavior rather than crediting Ant with it.
- Data plane: original signal and attribution; Linear issue identity, state/owner/relations; native OpenSpec artifacts and reciprocal links; GitHub branch/PR/revision/reviews/checks; bounded revision- and freshness-scoped evidence. Control plane: accountable coordinator, stage owner, explicit permission envelope, current executor/reviewer, resource ownership, dependency ordering, human decisions, pause/resume/recovery. These are existing-system responsibilities, not a new datastore or protocol.
- Linear status/assignee is not an atomic claim. Do not promise exactly-once dispatch or mutual exclusion without a verified mechanism. A PR, merged code, archived change, green prior check, worker success message, or status label alone is not acceptance. Re-read changed scope, PR head, checks, review threads, relations, and state before consequential mutations and whenever evidence may have changed.

## State transitions and handoff contract

| Trigger/state | Owner | Gate and output |
|---|---|---|
| New signal / new issue request | `linear-intake` | Verified source/identity, preserved signal, classified kind/relations, material gaps identified; unresolved executable request -> refinement. |
| Project Backlog/Todo sweep or selected unresolved work | `linear-refinement` | Bounded batch and remainder; requirements/context/decisions/dependencies/owner and kind-specific executable criteria; feature plan/links valid or explicit blocker. |
| Eligible Ready work + explicit execution grant | delivery `linear-triage` | Fresh issue/plan/head, actual executor/resource owner, satisfied dependencies; bounded execution and current proof. No grant or unavailable claim mechanism -> stop before external effect. |
| Author-complete exact revision | `review` / relevant `gates` | Independent requirements/diff/security/behavior review and current required checks; findings -> delivery owner; changed head invalidates previous evidence. |
| Accepted code artifacts | `close` / native OpenSpec owner | Accepted delta sync/archive on delivery branch as applicable, independent validation; this does not imply tracker Done/merge/deploy. |
| Merged/integrated/deployed/external outcome | explicit relevant human/operational owner | Each declared acceptance boundary needs its own evidence; merged PR alone is not deployed or user-accepted. |
| Any changed requirement, relation, owner, branch/head, check, review thread, merge, environment/outcome | current owner then `linear-sync` | Recompute affected readiness/evidence; reconcile, do not replay stale writes. |
| Resume, worker loss, API timeout/unknown result, duplicate/cancel/defer, partial PR/merge | `recovery` or responsible stage, then `linear-sync` | Inspect actual current state before retry/cleanup; preserve original signals, allocation and checkpoint. Unknown result never implies failure or success. |

Every stage packet uses existing six-section Jcode handoff contract: **Identity; Outcome & acceptance; Authority; Evidence & freshness; Ownership & dependencies; Checkpoint & next action**. Support many-to-many issue/change/PR/task allocations explicitly. Source snapshots, exact revision/check identifiers and observed timestamps bind claims. Distinguish requested, attempted, observed, accepted. Never let readiness fields, tracker text, web pages or worker messages expand permission.
